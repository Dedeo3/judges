# Architecture

## Hosting

- **Frontend + backend**: `apps/web` (Next.js) deployed as a single unit on **Vercel** — API routes under `src/app/api/**` run as Vercel Functions, no standalone server process.
- **Postgres**: **Neon** (serverless, free tier), pooled connection string for use from serverless functions. It also holds the short-lived, single-use WebAuthn challenges and pending bindings (`ephemeral_state` table, consumed with an atomic `delete ... returning`), so no separate Redis service is needed.
- **Contracts**: Foundry-deployed to Monad Testnet, then Monad Mainnet (Phase 9) — independent of web hosting.

See [deployment.md](deployment.md) for the runbook.

## Contracts

| Contract | Role |
|---|---|
| `JudgesVerifier` | Entry point. Rejects any Merkle root the `CommitmentTree` hasn't published, verifies the Groth16 membership proof, derives the wallet/action binding (`policyHash`), and consumes the nullifier. |
| `CommitmentTree` | Redesign B. Append-only history of the off-chain LeanIMT root of identity commitments; only the server's `rootPoster` may `postRoot`. `JudgesVerifier` gates on `isKnownRoot`, which is what makes membership — not just knowledge of a secret — the on-chain check. |
| `Groth16Verifier` | Generated by `snarkjs` from the Phase 5 trusted setup. Its verification key and `prover/build/judges_membership_final.zkey` are a matched pair — both committed. |
| `NullifierRegistry` | Domain-scoped nullifier uniqueness. `consume()` is restricted to `JudgesVerifier` via a one-shot, deployer-only `setVerifier`. |
| `MonadP256Adapter` | Monad's native `P256VERIFY` precompile (`0x0100`, EIP-7951). Deployed as a usable building block; **not** on `JudgesVerifier`'s path — see that contract's scope note. |
| `JudgesField` (library) | The one on-chain definition of the field prime, `hashToField`, and `policyHash`, mirroring `packages/crypto`. Pinned against it by `contracts/test/JudgesField.t.sol`. |
| `SybilResistantDAO` / `AgentRegistry` / `SybilResistantFaucet` | The three README §15 demos, each with its own nullifier domain. |

**Not built, deliberately**: README §9.2/§16 lists a `JudgesRegistry`. Its apparent job — credential, application, and binding records — is served by the Neon tables from Phases 1–2, which is where that data has to live anyway since it's queried off-chain. Nothing was deployed in its place.

## Nullifier domains

Each demo is deployed with a `domain` derived from its app-id string (`JudgesField.hashToField`).
The frontend must use the same string as its `appId`, since that becomes the circuit's
`applicationIdHash` public input. Separate domains are why acting in one demo doesn't spend a
credential's turn in another.

| App id | Used by |
|---|---|
| `judges-dao` | `SybilResistantDAO` |
| `judges-agent-registry` | `AgentRegistry` |
| `judges-faucet` | `SybilResistantFaucet` |
| `judges-demo` | the `/demo` page's plain prove flow |
